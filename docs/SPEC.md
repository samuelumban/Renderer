# Universal Remotion Render Studio

## Product Requirements & Technical Specification --- Windows Desktop

**Status:** Implementation specification\
**Target OS:** Windows 10/11 64-bit\
**Primary goal:** Import a Remotion project ZIP, inspect it, preview it,
and render it without changing the project's intended dependency
versions or polluting the computer with unused project files.

------------------------------------------------------------------------

## 1. Product vision

Build a lightweight Windows desktop application that manages Remotion
projects independently.

A user imports a ZIP generated by an AI coding tool. The application
inspects the project, prepares the required Node.js runtime and
dependencies, launches Remotion Studio for preview, and renders the
selected composition through the project's own Remotion CLI.

The application must **not** force every project to use one global
Remotion version. Project A may use a different Remotion version from
Project B. Each project must run using its own `package.json` and
lockfile.

The application is an orchestrator and user interface. Remotion remains
the rendering engine.

### Main principles

1.  Preserve the project as generated. Never silently upgrade or
    downgrade Remotion or its dependencies.
2.  Prefer project-local dependencies and isolated workspaces over
    global package installations.
3.  Keep the desktop application lightweight.
4.  Reuse safe caches, but impose limits and provide cleanup controls.
5.  Delete temporary working files after a job completes, while
    retaining the user's original ZIP and final rendered output.
6.  Preview and render must use the same prepared project environment.
7.  Make errors understandable and actionable.

------------------------------------------------------------------------

## 2. Important architecture decision: do not require Docker by default

Docker is useful for strict isolation, but it adds installation size,
background services, image storage, and operational complexity. Those
costs conflict with this product's lightweight requirement.

**Default architecture: native Windows process isolation.**

-   Desktop shell: **Tauri 2**.
-   UI: React + TypeScript.
-   Desktop/backend orchestration: Rust commands invoked by Tauri.
-   Remotion execution: child processes using Node.js and the project's
    local CLI.
-   Browser: the Chromium runtime supported by Remotion/Puppeteer,
    managed separately from the UI webview.
-   Package installation: npm, pnpm, or Yarn according to the project
    lockfile.
-   Video encoding: Remotion's supported rendering pipeline and FFmpeg
    dependencies.

Do not bundle Docker into the initial release. Keep an optional future
containerized mode as a possible advanced feature, not a requirement.

### Why Tauri instead of Electron?

Tauri generally produces a smaller desktop shell because it uses the
operating system's WebView2 rather than bundling a full Chromium runtime
into the application. Remotion still needs its own compatible browser
for rendering; do not assume the Tauri UI webview can replace Remotion's
rendering browser.

### Runtime strategy

-   Detect the Node.js version requirement from `package.json`
    (`engines.node`) and project configuration.
-   Support a managed, app-controlled Node.js runtime directory, with a
    small set of Node versions downloaded on demand.
-   Do not replace or modify the user's system Node.js installation.
-   If the project does not specify a Node version, use a documented
    compatible default and show it in the inspection report.
-   Record the exact runtime path and version used for every project.
-   Validate compatibility before installing dependencies.

A project may have native dependencies that behave differently across
Node versions or Windows environments. The app must report unsupported
cases instead of claiming every arbitrary project is guaranteed to work.

## 3. User workflow

### 3.1 Import

1.  User selects a `.zip` file or drops it into the app.
2.  App validates the archive and checks for unsafe paths/path
    traversal.
3.  App identifies the project root, even if the ZIP contains one
    enclosing folder.
4.  App checks for `package.json`, Remotion entry files, lockfiles, and
    likely project configuration.
5.  App asks the user to choose a project name if it cannot derive one.
6.  App copies/extracts the project into the app's managed workspace.

Do not execute scripts during archive inspection.

### 3.2 Inspect

Display a report containing:

-   Project name and detected root folder.
-   Remotion version and versions of relevant `@remotion/*` packages.
-   React version.
-   Node.js requirement and selected runtime.
-   Package manager.
-   Lockfile detected.
-   Install command that will be used.
-   Remotion entry point and detected compositions, where possible.
-   Font files found in the project.
-   External font references or likely missing fonts, where detectable.
-   Warnings and blocking errors.

The inspector must distinguish **confirmed missing dependencies** from
**possible issues**. Static scanning cannot reliably prove that every
CSS font family is available at runtime.

### 3.3 Prepare environment

Use the project's lockfile whenever present:

  -----------------------------------------------------------------------
  Lockfile                            Preferred install
  ----------------------------------- -----------------------------------
  `package-lock.json`                 `npm ci`

  `pnpm-lock.yaml`                    `pnpm install --frozen-lockfile`

  `yarn.lock`                         Yarn immutable/frozen install
                                      appropriate to the detected Yarn
                                      generation
  -----------------------------------------------------------------------

Rules:

-   Do not run `npm install` when a valid npm lockfile exists.
-   Do not regenerate or delete the user's lockfile automatically.
-   Do not install the latest Remotion globally.
-   Do not mix package managers in one project.
-   Do not silently change package versions to fix an error.
-   If no lockfile exists, explain that dependency resolution may not be
    reproducible and ask permission before generating one.
-   Capture stdout, stderr, exit code, duration, and the exact command.
-   Support cancellation.
-   Set a per-project install timeout and show progress.

Check that `remotion` and `@remotion/*` packages are version-compatible.
Report mismatches; do not automatically rewrite `package.json`.

### 3.4 Preview

-   Start Remotion Studio using the project's local CLI and selected
    Node runtime.
-   Bind the preview server to localhost only.
-   Allocate an available local port.
-   Open the preview in the app or the user's default browser.
-   Track the child process and terminate it when the user closes the
    preview or the app exits.
-   Use the exact prepared workspace and dependencies later used for
    rendering.
-   Show the selected composition, dimensions, FPS, and duration where
    available.

### 3.5 Render

Provide controls for:

-   Composition.
-   Output filename and destination.
-   Codec/container options supported by the installed Remotion version.
-   Scale/resolution options supported by the project.
-   Concurrency/CPU usage.
-   Frame range, where supported.
-   Render progress, current frame, elapsed time, and logs.
-   Cancel render.

Invoke the local Remotion CLI, not a globally installed CLI. Construct
arguments safely; do not concatenate untrusted shell strings. Use
process argument arrays.

Example conceptual command:

``` powershell
node .\node_modules\remotion\cli\remotion-cli.js render <composition-id> <output-path>
```

The exact executable path/command must be resolved from the installed
package and package manager. Do not hard-code a path that may differ
between package versions.

Write final output directly to the user-selected destination when safe,
or render to a temporary output file and move it into place only after a
successful render. Never leave a partial file named as if it were a
completed render.

## 4. Lightweight storage and cleanup policy

This is a core product requirement, not an optional enhancement.

### 4.1 Storage locations

Use a clear app-managed directory, for example:

``` text
%LOCALAPPDATA%\UniversalRemotionStudio\
  app/
  runtimes/
    node-vXX/
  workspaces/
    <project-id>/
      source/
      node_modules/
      temp/
  cache/
    package-manager/
    browser/
  logs/
  settings/
```

Final renders should default to a user-selected folder such as
`Videos\Remotion Renders`, not inside temporary workspaces.

### 4.2 What to keep

By default, retain only:

-   App settings.
-   Managed Node runtimes currently in use.
-   Original imported ZIP (optional setting; default: keep).
-   Project metadata and inspection report.
-   Final rendered video(s), in the user's chosen output folder.
-   A small rolling set of diagnostic logs.

### 4.3 What to delete after a successful render

After the render process exits successfully and the final output has
been verified:

-   Delete the project's temporary render files.
-   Delete generated preview/build temp files.
-   Stop and remove the preview server process.
-   Delete temporary extracted copies if the user chose one-time project
    mode.
-   Remove intermediate files created by the app.
-   Do not keep old render batches, frame sequences, or duplicate output
    copies unless the user explicitly asks.

**Important:** `node_modules` is not a temporary render artifact. It is
the installed dependency environment needed to reopen the same project
quickly. Offer two modes:

**Fast Reopen (default):** Keep the project's extracted source and
`node_modules` until the user removes the project or storage cleanup is
requested. This avoids reinstalling dependencies every time.

**Save Space:** After rendering, delete the extracted workspace
including `node_modules`, while retaining the original ZIP, project
metadata, and final output. Reopening the project will require
extraction and dependency installation again.

Provide a per-project choice and a global default. Never delete the only
copy of the user's source project without explicit consent.

### 4.4 Cache management

Package-manager caches can grow over time. Implement:

-   Configurable cache size limit (initial default: 5 GB).
-   Display current cache usage.
-   LRU cleanup of old cache entries where safe.
-   A **Clear package cache** action.
-   A **Clear unused Node runtimes** action.
-   A **Clean temporary files** action.
-   A storage breakdown by category.

Do not clear caches while an install or render is running. Do not delete
a runtime currently used by a project.

### 4.5 Automatic cleanup triggers

Run cleanup:

-   After a successful render.
-   After a cancelled render, once child processes have stopped.
-   When a project is removed.
-   On app startup, to recover stale temporary folders from a previous
    crash.
-   When the user clicks **Clean now**.

Cleanup must use a known list of app-created paths. Never recursively
delete arbitrary paths supplied by a ZIP or project file. Resolve and
validate paths to ensure they remain inside the app workspace before
deletion.

### 4.6 Storage settings UI

Show:

``` text
STORAGE

Project workspaces       2.4 GB
Node runtimes             180 MB
Package cache             1.1 GB
Browser cache             320 MB
Temporary files            45 MB

[ Clean temporary files ]
[ Clear package cache ]
[ Remove unused runtimes ]
```

The figures above are illustrative, not fixed requirements.

## 5. Font management

Font issues are common in AI-generated projects. Treat fonts as a
first-class inspection and troubleshooting feature.

### Detect

-   Scan project assets for `.ttf`, `.otf`, `.woff`, and `.woff2`.
-   Inspect CSS for `@font-face`, `font-family`, and external font
    imports.
-   Inspect HTML/CSS for Google Fonts references where possible.
-   Identify font files included in the ZIP and show their paths.
-   Warn when a font family is referenced but no corresponding bundled
    font is found. Label this as a warning unless runtime inspection
    confirms failure.

### Resolve

Preferred order:

1.  Use font files already bundled in the project through its existing
    CSS.
2.  Allow the user to add font files to a project-specific font folder.
3.  Provide an optional font library managed by the app.
4.  For fonts that must be visible to Chromium as installed fonts, use a
    controlled per-user/per-render font setup where technically
    supported on Windows; do not silently install fonts system-wide.

Do not download proprietary fonts without user authorization or a valid
license. External font downloads should be opt-in. Provide a way to
retry preview/render after adding fonts.

The app must not promise that merely detecting a family name proves the
correct font file is available. A font may be substituted by Chromium
without a hard error.

## 6. Project compatibility and error handling

### Common checks

-   Missing `package.json`.
-   No recognizable Remotion dependency.
-   Missing lockfile.
-   Lockfile/package-manager mismatch.
-   Incompatible Remotion and `@remotion/*` versions.
-   Unsupported Node.js requirement.
-   Dependency installation failure.
-   Missing browser/runtime requirement.
-   Missing or substituted fonts.
-   Composition not found.
-   Invalid render arguments.
-   Insufficient disk space.
-   Output folder not writable.
-   Browser launch failure.
-   FFmpeg/codec failure.
-   Project scripts attempting network access or other external actions.

### Error presentation

Every error should include:

1.  Plain-language summary.
2.  Relevant command and exit code.
3.  Short, useful excerpt from stderr.
4.  Likely cause (clearly marked as a hypothesis if not certain).
5.  Safe suggested action.
6.  **Copy diagnostics** button.

Do not automatically edit source files or package versions. Any repair
that modifies project files must show a diff/summary and ask for
confirmation.

### Logs

-   Store logs per project/job.
-   Rotate logs by size and age.
-   Default retention: last 10 jobs or 14 days, whichever is smaller.
-   Do not log secrets, environment tokens, or private values.
-   Add a **Delete logs** action.

## 7. Security requirements

ZIP files and AI-generated project code must be treated as untrusted.

-   Prevent ZIP path traversal (for example, `..\` paths).
-   Reject or safely handle symlinks and suspicious archive entries.
-   Set maximum ZIP size and extracted-size limits, configurable by the
    app.
-   Never execute package scripts during inspection.
-   Dependency installation can execute lifecycle scripts. Warn the user
    and require explicit approval before the first install for a
    project.
-   Offer a safer install mode that disables lifecycle scripts, with a
    clear warning that some projects may not work in that mode.
-   Bind preview servers to localhost.
-   Do not expose preview ports to the local network by default.
-   Do not run the app as Administrator.
-   Do not automatically change system PATH, global npm packages, system
    Node, or system fonts.
-   Keep project execution and file deletion restricted to the managed
    workspace and user-approved output paths.

### Project detail screen

Tabs:

-   Overview.
-   Environment.
-   Fonts.
-   Preview.
-   Render.
-   Logs.

### Render queue

For the first release, run one render at a time by default to avoid
memory pressure. Allow the user to increase concurrency only after
showing a warning about CPU/RAM use.

Queue states:

-   Waiting.
-   Preparing.
-   Rendering.
-   Completed.
-   Failed.
-   Cancelled.

A completed job should not retain temporary frame files or duplicate
intermediates. Keep only the final output and concise job metadata.

## 9. Performance requirements

-   Keep the desktop shell lightweight; do not bundle a second full
    browser into the UI shell.
-   Download Node runtimes and browser components only when needed.
-   Reuse a compatible runtime and browser installation across projects.
-   Keep project dependencies isolated, but do not duplicate Node
    runtimes per project.
-   Use a single render at a time by default.
-   Show a disk-space estimate before installation and rendering where
    feasible.
-   Check available disk space before extracting or installing
    dependencies.
-   Support cancellation of extraction, installation, preview, and
    rendering.
-   Avoid keeping full console output in memory; stream logs to rotating
    files and show a bounded tail in the UI.
-   Do not keep frame images after the render unless the user explicitly
    requests an image sequence.

## 10. Suggested implementation phases

### Phase 1 --- Working MVP

-   Tauri + React desktop shell.
-   Import and safely extract ZIP.
-   Detect project root, package manager, lockfile, Remotion version,
    and Node requirement.
-   Managed Node runtime.
-   Install dependencies using the existing lockfile.
-   Run Remotion Studio preview.
-   Render one composition to MP4.
-   Stream logs and progress.
-   Cancel jobs and terminate child processes safely.
-   Basic cleanup and storage display.

### Phase 2 --- Reliability

-   Font inspection and project font folder.
-   Better composition discovery.
-   Render queue.
-   Crash recovery and stale-temp cleanup.
-   Cache size limit and cleanup controls.
-   More complete diagnostics.
-   Per-project Fast Reopen / Save Space modes.

### Phase 3 --- Advanced features

-   Optional app-managed font library.
-   More codec and render options.
-   Environment snapshots.
-   Advanced compatibility diagnostics.
-   Optional Docker mode for projects that cannot be reliably supported
    natively.
-   Exportable diagnostic bundle.

Do not implement every advanced feature before the MVP can reliably
import, preview, render, and clean up a real project.

## 11. Data model (initial)

### Project

``` ts
type Project = {
  id: string;
  name: string;
  originalZipPath: string;
  workspacePath: string;
  projectRoot: string;
  packageManager: "npm" | "pnpm" | "yarn" | "unknown";
  lockfilePath?: string;
  remotionVersion?: string;
  nodeRequirement?: string;
  selectedNodeRuntime?: string;
  storageMode: "fast-reopen" | "save-space";
  createdAt: string;
  lastOpenedAt?: string;
};
```

### Render job

``` ts
type RenderJob = {
  id: string;
  projectId: string;
  compositionId: string;
  outputPath: string;
  status:
    | "waiting"
    | "preparing"
    | "rendering"
    | "completed"
    | "failed"
    | "cancelled";
  startedAt?: string;
  finishedAt?: string;
  exitCode?: number;
  logPath: string;
  temporaryPaths: string[];
};
```

Never trust `temporaryPaths` from project files. Only the application
may create and register cleanup paths.

## 12. Acceptance criteria

The MVP is accepted only when all of the following are demonstrated:

1.  Import a valid Remotion ZIP without requiring the user to manually
    extract it.
2.  Correctly identify the project's Remotion version from its
    dependencies.
3.  Use the project's own lockfile and local CLI.
4.  Run two projects with different Remotion versions without changing
    global Remotion installations.
5.  Avoid changing the user's system Node.js installation.
6.  Preview and render the same prepared workspace.
7.  Render a valid output file and verify that it is non-empty.
8.  Show actionable diagnostics when installation or rendering fails.
9.  Cancel a render and stop its child processes.
10. Clean temporary render files after completion.
11. Preserve the original ZIP and final output.
12. Offer a Save Space mode that removes the extracted workspace and
    `node_modules` after rendering.
13. Never delete a user's source ZIP or final output during automatic
    cleanup.
14. Recover and clean stale temporary folders after an app crash.
15. Show storage usage and allow safe cache cleanup.

## 13. Development instructions for the AI coding agent

Build this application incrementally. Before implementation:

1.  Inspect the target Windows environment and available build tools.
2.  Create a concise architecture plan and folder structure.
3.  Confirm the current stable Tauri 2, Rust, React, and TypeScript
    setup using their official documentation.
4.  Identify the supported Remotion CLI invocation for the versions
    being targeted.
5.  Do not assume every Remotion project uses npm; detect lockfiles.
6.  Do not hard-code one Remotion version.
7.  Do not use Docker as a mandatory dependency.
8.  Keep all runtime, workspace, cache, and output paths explicit and
    configurable.
9.  Implement safe process management and cleanup before adding advanced
    UI features.
10. Add automated tests for ZIP path traversal, project detection,
    lockfile detection, version inspection, cancellation, and cleanup
    boundaries.

Use small modules with clear responsibilities:

``` text
src/
  components/
  pages/
  hooks/
  types/
  services/

src-tauri/
  src/
    commands/
    project/
    runtime/
    package_manager/
    remotion/
    preview/
    render/
    storage/
    cleanup/
    diagnostics/
```

The exact folder structure may evolve, but keep UI, project inspection,
process execution, storage management, and cleanup separate.

### Final product definition

A lightweight Windows desktop manager for Remotion projects that accepts
AI-generated ZIPs, preserves each project's own versions, prepares
dependencies on demand, previews and renders through the local Remotion
CLI, and automatically removes temporary files so old render batches do
not accumulate.
